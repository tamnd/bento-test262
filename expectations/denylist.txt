# Quarantine list: tests that must never reach a worker.
#
# A line here is not a failing test. It is a test whose lowering or build is
# known to exhaust memory or wedge the toolchain badly enough to threaten the
# whole machine, so the run skips it entirely rather than record a verdict it
# dared not produce. This is a last resort for a specific landmine; the general
# memory guards (worker recycling, the per-process soft memory limit, and the
# bounded go build -p) are what keep an ordinary run safe. See the README.
#
# Format: one substring per line, matched against a test's path relative to the
# test262 root, the same match --grep uses. A blank line or a line starting with
# # is ignored, so keep a note next to each entry saying why it is here.

# Recorded compiler crash: the sloppy-mode generator with a computed property
# name whose expression is a yield crashes the lowering path outright. Kept out
# of the run so a crash can never wedge a worker slot; revisit when the generator
# lowering lands.
test/language/expressions/object/method-definition/generator-prop-name-yield-expr.js

# Memory blowup: a named function expression that reassigns its own name inside
# an eval in its body drives the checker to infer a self-referential type that
# the lowerer then walks without bound. Before the typeExpr node budget landed in
# bento this climbed past 6 GB in seconds and OOM-rebooted the machine; the
# budget now hands it back, but it stays quarantined so an older bento binary
# cannot trip the same landmine. Only the plain-function forms reach the blowup;
# the async and generator siblings hand back at the front end first, so they are
# left in the run. Revisit when the name-in-body-in-eval type lowers.
test/language/expressions/function/named-no-strict-reassign-fn-name-in-body-in-eval.js
test/language/expressions/function/named-strict-error-reassign-fn-name-in-body-in-eval.js

# Dense-array memory blowup: the test writes an array element at a power-of-two
# index that doubles up to 2^32, so the last write lands near index 4.29 billion.
# JavaScript keeps that as a sparse array with no storage for the holes, but the
# dense array core stores a zero for every empty slot, so the write tries to grow
# the backing slice to billions of elements and exhausts memory. Before the Set
# growth cap landed in bento the run OOM-killed the process (and on a tight box
# threatened the machine); the cap now throws a RangeError instead, but the test
# stays quarantined so an older bento binary cannot trip the blowup and so the
# thrown RangeError does not read as a real failure. Revisit when the sparse array
# representation lands and the indices store without a dense fill.
test/built-ins/Array/S15.4_A1.1_T10.js
